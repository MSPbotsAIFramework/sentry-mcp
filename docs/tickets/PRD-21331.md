## Product design

### Goals / non-goals

**Goals** (v1, first version of the connector):
- Let an agent see which Sentry organizations and projects the configured token can reach.
- Let an agent find and triage error issues: list issues with Sentry's search syntax, read one issue's detail, and change its status (resolved / unresolved / ignored), assignment, bookmark, and priority.
- Let an agent drill into the events behind an issue: list the events that make up an issue and read one event's full detail (stack trace, tags, user context).
- Let an agent look up organization members, to resolve a human name into the `assignedTo` value `sentry_update_issue` needs.
- Let an agent read release and deploy history, and record a new release or deploy when asked (e.g. "we just shipped v1.4.2, log it in Sentry").

**Non-goals (v1)**:
- Deleting issues, events, projects, or organizations. Nothing in the ticket asks for destructive cleanup, and Sentry's own issue-lifecycle model is "resolve / ignore", not delete — there is no documented delete-an-issue endpoint in the public API.
- Alert rule / monitor configuration (Monitors & Alerts), Dashboards, Discover & Performance queries, Replays, Profiling, SCIM provisioning, and third-party Integrations management. All are administrative or analytics surfaces orthogonal to "an agent triaging errors," most Enterprise-plan-oriented; see "Decisions made by DEV01" for the per-group reasoning.
- Creating/deleting projects or organizations, client-key (DSN) management, service hooks, spike protection, inbound filters, member invite/role management (write side). All organization-administration, not error-triage.
- OAuth2 app registration (multi-tenant consent flow). v1 authenticates with a user's own Sentry Auth Token (bearer), matching Sentry's own "recommended" token type.

### Acceptance criteria

- **AC1** — Given a valid `X-Sentry-Auth-Token`, `sentry_list_organizations` returns the organizations (id, slug, name, status) the token can access.
- **AC2** — Given a request to any tool without `X-Sentry-Auth-Token`, the server returns HTTP 401 with a body listing the required header.
- **AC3** — Given an organization slug, `sentry_list_projects` returns that organization's projects (id, slug, name, platform).
- **AC4** — Given an organization slug and a project slug, `sentry_get_project` returns that project's detail (id, slug, name, platform, team(s), dateCreated).
- **AC5** — Given an organization slug, `sentry_list_issues` returns issues matching Sentry's `query` search syntax (default `is:unresolved` when `query` is omitted), optionally scoped to one or more `project` slugs, sorted by the requested `sort`, paginated via cursor.
- **AC6** — Given an organization slug and an issue id, `sentry_get_issue` returns that issue's detail: title, culprit, status, level, counts, firstSeen/lastSeen, assignedTo.
- **AC7** — Given an organization slug, an issue id, and one or more of `status` / `assignedTo` / `isBookmarked` / `priority`, `sentry_update_issue` applies exactly those fields and returns the updated issue; fields not passed are left unchanged.
- **AC8** — Given an organization slug and an issue id, `sentry_list_issue_events` returns the events belonging to that issue, paginated.
- **AC9** — Given an organization slug, an issue id, and an event id, `sentry_get_issue_event` returns that event's full detail (exception/stacktrace entries, tags, user, contexts).
- **AC10** — Given an organization slug, `sentry_list_members` returns the organization's members (id, email, name, orgRole, pending).
- **AC11** — Given an organization slug, `sentry_list_releases` returns releases, optionally scoped by `project`, paginated.
- **AC12** — Given an organization slug and a release version, `sentry_get_release` returns that release's detail (version, projects, dateCreated, dateReleased, newGroups, commitCount).
- **AC13** — Given an organization slug, a `version`, and a list of `projects`, `sentry_create_release` creates the release (optionally with `ref`, `url`, `dateReleased`) and returns the created release; calling it again with the same `version` returns the existing release rather than erroring (Sentry's own create-release semantics are upsert-by-version).
- **AC14** — Given an organization slug, a release `version`, and an `environment`, `sentry_create_deploy` creates a deploy record for that release (optionally with `name`, `url`, `dateStarted`, `dateFinished`, `projects`) and returns the created deploy.
- **AC15** — Given the upstream Sentry API returns 400 / 401 / 403 / 404 / 429 / 5xx / a network error, every tool returns the structured error envelope `{"error":{"code","message","retryable"}}` with the code from the fixed vocabulary — never raises an exception to the caller.
- **AC16** — Every list tool caps its page size (default ≤ 50, hard max ≤ 100 — Sentry's own documented cap) and its serialized result at 20000 characters, and reports `has_more` / a `next_cursor` when a page was cut.
- **AC17** — The raw `X-Sentry-Auth-Token` value never appears in logs, error messages, or tracebacks.
- **AC18** — Two concurrent requests carrying different tokens (and, if set, different `X-Sentry-Base-URL` values) never see each other's credentials or data (per-request isolation, no shared mutable state between tenants).

### Open questions

- **Q1 (not blocking, assumption stated)**: The ticket names no specific Sentry capability. This design assumes "connect Sentry so an agent can see projects, triage issues, and log releases/deploys" is the intended scope, matching the generic Conduit template and the shape of every other connector built from the same template batch (Hudu, Box, Plaid, Figma). If the requester wants something narrower or broader (e.g. alert-rule management, performance/Discover queries), say so in a comment and move this ticket back to `5b - ready for groom`; v1 ships against the assumption above.
- **Q2 (not blocking)**: Sentry supports self-hosted/on-premise installations with a different API host than `sentry.io`. v1 defaults to `https://sentry.io` but accepts an optional `X-Sentry-Base-URL` override (see "Decisions made by DEV01") rather than hardcoding one host the way Figma did — self-hosted Sentry is common enough in this org's MSP customer base that deferring it felt riskier than for Figma's niche government-cloud case.

## Tech design

### Conclusion

Build `sentry-mcp` from scratch (vendor-mcp-development main line A) against Sentry's public REST API (`https://docs.sentry.io/api/`, version `v0`), authenticating with a Sentry Auth Token carried in the `X-Sentry-Auth-Token` header on every request, plus an optional `X-Sentry-Base-URL` header for self-hosted instances (default `https://sentry.io`). 13 tools across 5 capability groups (organizations/projects, issues, issue events, members, releases/deploys). No gateway change needed (not a builtin-OAuth vendor, see "Current state").

### Option analysis

- **Bearer auth token over OAuth2 app (chosen)**: Sentry's own docs (`docs.sentry.io/api/auth/`, fetched 2026-11-02) call "Authentication Tokens" (created via an internal integration, or a personal "User Auth Token") the **recommended** method, and list OAuth2 as an alternative "for third-party applications requiring user authorization." A token needs no app registration, no redirect URI, no consent-screen hosting — the account owner generates one in Sentry settings and pastes it into the MSPbots Connector UI, the same "bring your own API key" flow as every other first-party MCP in this org. OAuth2 would let MSPbots broker consent without the user seeing a raw token, but needs an app registration and token-refresh logic for a ticket that names no specific need. Deferred; see "Decisions made by DEV01."
- **Organization-scoped endpoints (`/api/0/organizations/{org}/issues/...`) over project-scoped (`/api/0/projects/{org}/{project}/issues/...`)** for issues: Sentry's own "List a Project's Issues" page (fetched 2026-11-02) states "This endpoint has been replaced with the Organization Issues endpoint" — using the project-scoped pair for issues/events would mean building against a page that documents its own replacement. The organization-scoped issue/event endpoints are used throughout (AC5–AC9).
- **`organization_slug` as a required tool argument, not baked into credentials**: Sentry's newer Organization Auth Tokens are scoped to one org, but legacy/User Auth Tokens can reach several; there is no "list my single org" shortcut to rely on. So every tool takes `organization_slug` explicitly (`sentry_list_organizations` is how an agent discovers it), the same pattern Figma used for `file_key`/`team_id` rather than assuming one fixed scope per credential.
- **Mirror every endpoint 1:1** vs. **cover capability groups and cut analytics/admin endpoints**: rejected 1:1 mirroring — SOP §2 caps a service at ≤ 20 tools and asks for "capabilities not endpoint mirrors." Sentry's documented endpoint surface (Dashboards, Discover/Performance, Replays, Profiling, Integrations, SCIM, Monitors & Alerts, client keys, service hooks, spike protection, member role writes) is large and mostly analytics/administration; see "Decisions made by DEV01" for the per-group reasoning.

### Data & API contract

**Credential headers** (declared in README, read verbatim in `server.py`):

| Header | Required | Meaning |
|---|---|---|
| `X-Sentry-Auth-Token` | yes | Sentry Auth Token (Settings → Auth Tokens, or an internal integration token, in the Sentry web app). Scopes needed: `org:read`, `project:read`, `project:releases`, `event:read`, `event:write`, `member:read`. |
| `X-Sentry-Base-URL` | no | API host for self-hosted/on-premise Sentry. Defaults to `https://sentry.io` when omitted. |

Missing the required header → `401 {"error":"Missing credentials","message":"Missing header(s): X-Sentry-Auth-Token","required_headers":["X-Sentry-Auth-Token"]}` (AC2), same envelope shape as `hudu_mcp`'s `GatewayCredentialsMiddleware`.

**Pagination**: list endpoints use Sentry's own opaque `cursor` (from the response's `next_cursor`/`Link` header) passed straight through as a `cursor` input — not an offset model, Sentry's own cursors are not guaranteed to be offsets (confirmed on the "List a Project's Issues" and "List an Organization's Releases" pages, both documenting `cursor`/pagination this way). Every list tool also caps the serialized result at 20000 chars via the shared `dump_json_capped` truncation (same mechanism as `hudu_mcp/_json.py:30`), degrading gracefully (shortens long fields, then cuts the list and reports `has_more`) rather than ever dropping output silently (AC16).

**Backward compatibility**: not applicable — new repo, no existing callers.

### Key flow / sequence

1. Gateway receives a tool call from an agent, resolves the tenant's stored Sentry Auth Token (and base URL, if self-hosted), and forwards the HTTP request to `sentry-mcp` with `X-Sentry-Auth-Token` (and optionally `X-Sentry-Base-URL`) set.
2. `GatewayCredentialsMiddleware` reads the headers; missing the required one → 401 (ends here); a malformed base URL → 400. Otherwise sets `SentryCredentials` on a `contextvars.ContextVar` for the duration of this request.
3. The called tool builds a `SentryClient` from the context var and calls the matching Sentry REST endpoint under `{base_url}/api/0/...`.
4. `SentryClient.request()` retries once or twice on `429`/`5xx`/network error (GET only; a `PUT`/`POST` is never retried so an issue update or release/deploy creation is never double-applied), honoring `Retry-After` and the `X-Sentry-Rate-Limit-Reset` header when present.
5. On success, the tool shapes the response into the table above and returns it through `dump_json_capped`. On failure, `run_tool()` catches `SentryError`/`ValueError`/any other exception and returns the structured error envelope — the caller never sees a traceback (AC15).
6. `finally` in the middleware resets the context var so the next request (possibly a different tenant, since the container is shared) starts clean (AC18).

### Non-functional

- **Idempotency / concurrency**: reads are naturally idempotent and safely retried; `sentry_update_issue` (PUT) and `sentry_create_deploy` (POST) are never retried by the client on failure — a timed-out call returns `upstream_error` and lets the agent decide whether to re-ask, rather than risk a duplicate deploy record or an unintended repeated status flip. `sentry_create_release` (POST) is Sentry's own upsert-by-version (AC13), so a client-side retry of a creation that actually succeeded upstream is harmless by design — annotated `WRITES_IDEMPOTENT` rather than plain `WRITES`.
- **Performance**: `_CALL_BUDGET_SECONDS = 100` (under the gateway's 120s tool-call timeout, same margin as `hudu_mcp`/`figma_mcp`). `sentry_get_issue_event` on a large exception/stacktrace payload can be sizable; `dump_json_capped` prevents an oversized response from ever being returned whole (AC16).
- **Security**: `X-Sentry-Auth-Token` is read once per request from the header, stored only in a per-request `contextvars.ContextVar`, never logged or echoed in error messages (`SentryCredentials.__repr__` redacts it, mirroring `HuduCredentials`), never persisted to disk or environment. No cookies are sent or stored (shared `httpx.AsyncClient` uses a reject-all cookie jar, same as `hudu_mcp`) since the HTTP client is shared across tenants in one process.
- **Multi-tenant isolation**: one process serves every tenant; nothing about a request (token, base URL, response data) is cached or stored outside that request's `contextvars.ContextVar`, so two concurrent calls with two tenants' tokens cannot see each other's data (AC18). No module-level or global mutable state holds credentials or results.
- **Observability**: each upstream call logs method/path/status/duration/attempt (no token, no response body) at INFO; unexpected exceptions log at WARNING with the exception type only — same logging contract as `hudu_mcp/api_client.py:153-157` and `tools/_common.py:140-147`.

### Risks & dependencies

- **Risk**: Sentry's rate limits are per-endpoint and per-caller-identity (not bypassed by using multiple tokens), with exact numeric thresholds undocumented publicly (confirmed on `docs.sentry.io/api/ratelimits/`). Mitigated by keying retry/backoff off the live `429` + `Retry-After` + `X-Sentry-Rate-Limit-Reset` response rather than a hardcoded budget (same approach as every other MCP in this org).
- **Risk**: `sentry_list_issues`/`sentry_list_issue_events` on a high-volume project can return many pages; mitigated by cursor pagination plus `dump_json_capped`, not a correctness risk.
- **Dependency**: none on another ticket or repo. Self-contained, single-repo change.
- **Dependency (soft)**: v1 assumes a self-service Sentry plan is sufficient for all 13 endpoints (Organizations, Projects, Events & Issues, Releases, Members are all core resources, not flagged Enterprise-only anywhere in the fetched docs, unlike Figma's Variables/library scopes). If a real test account later shows an endpoint gated behind a specific plan tier, that surfaces as a self-test finding in the dev leg, not a design-time blocker.

### Decisions made by DEV01

(Posted verbatim in a separate `[DESIGN DECISIONS]` comment per `mcp-track.md` §2.4.)

- **Bearer auth token over OAuth2 app** — Sentry's own docs call it the recommended method for integrations; no Sentry OAuth app registration, redirect URI, or token-refresh logic needed. Alternative not chosen: register a Sentry OAuth2 app for a brokered consent flow (bigger first version, no ticket requirement calling for it).
- **Optional `X-Sentry-Base-URL` header, default `https://sentry.io`** — unlike Figma (one fixed host, government cloud deferred as an open question) or Plaid (fixed sandbox/production hosts), Sentry ships a documented, common self-hosted/on-premise deployment model; MSPbots' MSP customer base plausibly includes on-premise Sentry users. Alternative not chosen: hardcode `sentry.io` and defer self-hosted the way Figma deferred government cloud — rejected because self-hosted Sentry is a mainstream deployment option (unlike Figma Gov's narrow niche), not a speculative edge case.
- **Organization-scoped issue/event endpoints over project-scoped** — Sentry's own "List a Project's Issues" page states it "has been replaced with the Organization Issues endpoint." Alternative not chosen: build on the documented-superseded project-scoped pair (would need redoing immediately).
- **`organization_slug` as an explicit tool argument on every tool, not inferred** — a Sentry Auth Token is not guaranteed to be scoped to exactly one organization (legacy User Auth Tokens can reach several); `sentry_list_organizations` is how an agent discovers which slug(s) it can use. Alternative not chosen: assume a single org per credential and omit the argument (would break for any multi-org token).
- **Excluded Monitors & Alerts (cron monitor / alert rule configuration)** — administrative configuration of *how* Sentry alerts, not reading or triaging the errors themselves; the generic "connect Sentry" ask does not call for it. Alternative not chosen: include alert-rule CRUD (scope creep beyond anything any comment on this ticket asked for; can be added as a follow-up main-line-B ticket if someone asks for alert automation specifically).
- **Excluded Dashboards, Discover & Performance, Replays, Profiling** — these are analytics/observability surfaces for humans exploring trends and session replays, not the "triage an error issue" workflow this connector targets. Alternative not chosen: build them (large surface, no ticket signal that an agent needs performance/replay data specifically).
- **Excluded Integrations management, SCIM, client keys (DSN), service hooks, spike protection, inbound filters, member role writes** — all organization-administration features orthogonal to error triage, and several (SCIM, integrations) are Enterprise-plan-oriented. Alternative not chosen: build them (out of scope for a per-tenant error-triage connector; also higher blast-radius admin writes that were judged not worth the risk for a ticket with no specific ask).
- **No issue-delete tool** — Sentry's documented issue lifecycle is resolve/ignore, not delete; there is no delete-an-issue endpoint in the public API to wrap. Not a design choice to defer, there is nothing to build.
- **`sentry_update_issue` takes multiple optional fields in one tool rather than one tool per field** — Sentry's own `PUT` endpoint already accepts a partial-update body with any combination of `status`/`assignedTo`/`isBookmarked`/`priority`/etc.; splitting into `sentry_resolve_issue`/`sentry_assign_issue`/`sentry_bookmark_issue` etc. would multiply tool count for no behavioral gain (SOP §2 "capabilities not endpoint mirrors"), and an agent naturally wants to set several of these at once (e.g. "resolve and assign to me").
